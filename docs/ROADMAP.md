## 3. 决策记录（长期沉淀）

> 每条格式：`YYYY-MM-DD 决策 → 理由`。当天细节见 `docs/devlog/`。

- **2026-10-11 仓库根 = 项目根，`GAME/` 作引擎目录** → 让文档、美术源文件、代码、导出物全部在一个仓库内；日后加构建脚本/发布物不用挪窝。符合 project-management skill 的「仓库根=项目根」约定。
- **2026-10-11 `DEV/` 定位为开发草稿区** → 原型阶段允许混乱，正式资产必须有唯一的规范位置；草稿稳定后再"晋升"到 `scenes/`、`scripts/`。（用户原话："DEV是开发草稿区"）
- **2026-10-11 修正目录拼写 `assest→assets`、`scense→scenes`、`script→scripts`** → 趁两个场景 `.tscn` 还没有任何 `res://` 交叉引用时改名，零风险；拼写错误的目录名会长期污染检索与肌肉记忆。
- **2026-10-11 文件树模板以"仓库内文档 + 可复制骨架"形式沉淀** → Godot 官方 Project Manager 目前不支持自定义项目模板（见 [proposal #3388](https://github.com/godotengine/godot-proposals/issues/3388)、[discussion #11935](https://github.com/godotengine/godot-proposals/discussions/11935)），因此用「复制骨架」替代官方的"新建时选模板"。
- **2026-10-11 模板必须自带默认主场景 `scenes/Main.tscn`** → 新建的 Godot 工程没有 `run/main_scene` 时，按 F5 会报 `Error: Can't run project: no main scene defined`。工程起盘期这是"第一个必踩的坑"，属于模板应当消除的摩擦，不该留给使用者。
- **2026-10-11 渲染器 `Forward Plus` → `Compatibility`（用户拍板）** → 2D 游戏用 Compatibility：兼容性最好、包体更小、低端机友好；同步改 `config/features` 并清掉无用的 `d3d12` 驱动设置。改渲染器越晚越麻烦，故在 M1 前定。
- **2026-10-11 `SORCE/` → `SOURCE/`（用户拍板"改名"）** → 与 `assest`/`scense`/`script` 同属拼写统一问题；趁无外部引用一次改净。
- **2026-10-11 `DEV/` 不加 `.gdignore`（用户拍板"不要加"）** → 草稿区的价值就在于能在编辑器里直接运行验证；加了会被引擎跳过扫描、无法运行。
- **2026-10-11 模板抽出独立仓 `../godot-game-template/`（用户拍板"单独抽出"）** → 模板是跨项目资产，与具体游戏解耦后才有单一事实源；用 `git subtree split` 把 `templates/` 的提交历史一并带过去，避免"复制一份没历史的目录"。
- **2026-10-11 项目目的明确为「学习技术美术」（用户原话）** → 「这个项目主要目的是学习技术美术」。据此**新增 M4 技术美术研究为"一等公民"里程碑**（不再是"最后打磨"），并定取舍原则：出现取舍时优先选"能学到东西"的方案。技美实验与技法沉淀记入新建的 `docs/tech-art-log.md`（按技法主题，非按日期）。
- **2026-10-11 框架选型三项（用户确认）** → ①**全局状态机 + 场景管理器（Autoload）**：任何地方能读游戏状态，技美做全屏特效时也需要；②**单主场景 `World` + `UILayer` 并列**：暂停时只停 World、UI 仍响应（`change_scene_to_file` 换场景会把游戏画面丢掉，不适用）；③**UI 先用内置字体**：像素字体的缩放/字号调优属技美阶段。据此新增 **M1.5 整套框架**里程碑（用户指定为下一步：开始菜单 + 暂停界面）。
- **2026-10-11 文件树按功能重组（用户确认方案）** → ①障碍物系统从 `DEV/` **转正**：它已被主场景引用，事实晋升（判据：一被正式场景引用就不再是草稿）；按功能分组 `scripts/obstacle/` + `scenes/obstacle/`，用户理由「**以后可能会增加不同种类与属性的 obstacle**」。②`tools/` 二分 `engine/` + `debug/`，用户原话「**我发布游戏时肯定会删掉调试工具**」——分开才能让"删调试工具"变成删一个目录。
- **2026-10-11 经验回流到跨项目模板 v0.3** → 本次重构的两条判据（tools 二分、功能分组）写进 `docs/PROJECT_TREE_TEMPLATE.md` §2.6/§2.7 并同步独立模板仓骨架，避免下个项目重犯。
- **2026-10-11 两个仓推送为 GitHub 公开仓** → dummy-bird 与 godot-game-template 分别推送到 `MyrChRya2/dummy-bird`、`MyrChRya2/godot-game-template`；推送后核对本地/远端 HEAD、提交数、文件树、`.dsh-meow` 未入库，全部一致。
- **2026-10-11 屏幕方向定为横屏（用户拍板）** → 用户原话：「我依然倾向于横屏，类似于滑雪大冒险」。参照对象是横屏侧视的跑酷形态，因此构图走向为**横向推进 + 前后景视差**，而非竖屏的上下管道排布。横屏同时解锁了基础视口 320×180（16:9）与 `expand` 拉伸（按需扩展短轴、无黑边）的选择。
- **2026-10-11 图标暂用 Godot 默认图标占位（用户拍板）** → 用户原话：「icon.svg先用godot默认图标占位」。因此该文件作为第三方内容登记在 `PROJECT_INDEX.md` 第八节，**正式发布前必须替换为原创图标**（否则商店素材里会带着 Godot 的默认图标）。
- **2026-10-11 游戏定位（用户原话）**：「我想做一款类似于笨鸟先飞的点击跳跃游戏，计划在网页端Itch.io与移动端Taptap发布。游戏为2D像素风格，无剧情设计。目前定位先这样，随着项目的推进再慢慢调整。」→ 落成 `GDD.md` §1，并把定位分「锁定档」（2D 像素/单键点击跳跃/无剧情/网页+移动双端）与「可调档」（手感参数、数值、美术细节、商业模式）两档，避免小调整引发返工。
- **2026-10-11 目标平台决定「像素渲染地基」必须先做** → 2D 像素风要求关闭纹理过滤（实测当前仍是 Linear 默认），且网页与移动双端对分辨率/缩放/触屏的要求彼此约束；这类设置一旦素材开画后再改，代价是全部素材重做，故升为 M1 第 1 项任务。
- **2026-10-11 Web 导出面向 itch.io 必须用单线程** → itch.io 不发送 COOP/COEP 响应头，而 Godot 多线程 Web 导出依赖 `SharedArrayBuffer`，会加载失败；官方文档明确建议面向 itch.io 时关闭线程支持。第三方托管（如自配 COOP/COEP 头的服务器）才可用多线程。
- **2026-10-11 两个仓采用 MIT 许可（用户拍板）** → 用户最初想要 CC0，但 CC0 明文排除专利授权、不是为软件设计的许可证；且两仓当时无任何原创美术（`SOURCE/` 为空，唯一图形文件 `icon.svg` 是 Godot 官方默认图标），CC0 擅长的素材场景并不存在。选 MIT 同样达到"最大程度开放"（允许闭源商用/修改/再分发）。未来若给美术素材单独授权（如 CC0），代码保持 MIT。
- **2026-10-11 不做 EditorPlugin 生成目录（用户拍板"不要加"语境下默认）** → 插件必须先存在于工程内才能运行，绕不过"新建工程时尚无工程"的先有鸡还是先有蛋问题。
- **2026-10-11 主场景用 `tools/set_main_scene.gd` 写入，而非手改 `project.godot`** → 走引擎的 `ProjectSettings.save()`，落盘格式与编辑器菜单设置完全一致（UID 引用等细节由引擎决定）；手写文本有格式漂移风险。
